## 二、与计划书的差异与取舍（答辩口径）

| 计划书 | 实际交付 | 原因与影响 |
|--------|----------|------------|
| Redis 缓存/队列/锁 + Celery + Beat | **Django DatabaseCache**（规则缓存 TTL 300s、限流计数、`cache.add()` 分布式锁）+ **`manage.py beat` 循环** | 演示环境零额外中间件，依赖更少更稳；接口等价，切回 Redis/Celery 只需改 `CACHES` 与任务守护方式 |
| MySQL 8 | MySQL 8.0.34 + **Django 5.2 LTS** | 本机 MySQL 为 8.0.34，Django 6.x 要求 8.4+；锁定 LTS 更稳 |
| 微信授权登录为可选增强 | 仅保留占位函数 | 无已备案 AppID，账号密码登录为主（H5 亦可演示） |
| 取件凭证/送达凭证「关联文件」 | 各一个凭证文件 FK | 单凭证足够演示，多凭证可后续改 M2M，不影响资金与状态机 |
| 「已接单 → 待取件 → 配送中」三态 | 保留 `picked`（待取件）为合法状态，取件打卡一次直达 `delivering` | 避免多余的「到达取件点」操作；`picked` 仍可由异常/人工路径进入，状态集与筛选不变 |
| 学生「并致订单关闭」才记爽约 | 学生取消时**未填理由**即记 −10；填写理由视为有理由不扣分 | 原表述无法自动判定「无理由」，用「是否填写理由」作为可执行口径，已写入用户手册 |
| 已完成订单申诉 | 仲裁只处理**信用/评价争议**，不回溯已结算资金 | 修复资金凭空生成缺陷（见测试报告 Bug #1） |
| 地图/实时聊天/WebSocket | 未做（计划书即明确不做） | 文字地址 + 轮询消息 |
| `docs/openapi.yaml` | 由 drf-spectacular 生成，非功能性接口以契约文档为准 | APIView 未逐接口注解 serializer，生成物为骨架；`docs/API契约.md` 为权威口径 |

## 三、答辩演示脚本（约 8 分钟）

**准备**：`manage.py runserver`、`manage.py beat`、`admin-web npm run dev` 三进程；数据库已 `seed_demo`。

1. **管理端看板（1 分钟）**：`admin/Admin@123` 登录 → 数据看板三图（订单量趋势、信用分布、资金流水）→ 指出托管监控「平台账户 = Σ托管中流水 ✅」。
2. **学生发单与支付（1.5 分钟）**：小程序/H5 用 `s001/Student@123` → 发布需求（平台代付，预估 20 元）→ 去支付 → 强调页面常驻「模拟资金，无真实交易」。
3. **跑腿员接单与打卡（1.5 分钟）**：切 `r001/Runner@123` → 待接单大厅 → 接单 → 取件打卡（自动置垫付）→ 送达打卡填实际物品费 16.50。
4. **确认与结算（1.5 分钟）**：学生确认完成 → 酬金 = 9.90 + min(16.50, 20.00) = 26.40 → 差额 3.50 已退回学生 → 双向互评 → 双方各 +1 完成分、被评方按星级加减。
5. **提现闭环（1 分钟）**：跑腿员提现 → 余额立即冻结扣减 → 管理端提现审核通过（或驳回看余额回滚 + 原因）。
6. **风控与仲裁（1.5 分钟）**：跑腿员对差评发起申诉 → 订单转「申诉中」（资金留托管）→ 管理端仲裁按比例出账 → 展示信用恢复记录与操作日志。
7. **收尾（0.5 分钟）**：展示 `pytest` 39 项通过 + 覆盖率 73% + 冒烟 22/22，说明对账三恒等式。

**演示顺序建议**：先跑通主流程，再演示异常（自接单被拒、配送中禁止取消、重复确认不重复结算、并发接单仅一人成功）。

## 四、已知限制与后续建议

1. 小程序真机需填入微信小程序 AppID；未做微信授权登录。
2. 管理端 `npm run dev` 默认绑定 IPv6 `::1`，若后端只监听 IPv4，访问用 `http://localhost:5173` 或给 vite 加 `host: '127.0.0.1'`。
3. OpenAPI 生成物为骨架，若要正式对外发布建议逐接口加 `@extend_schema` 注解。
4. 演示视频需人工录屏（离线环境未生成）。
5. 生产化建议：接入真实对象存储（替换本地 media）、加 Redis + Celery、加接口幂等键统一中间件、加操作日志的字段级审计。
